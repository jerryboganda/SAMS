## 2026-07-31 — Phase 1 database (db-engineer): migrations, models, seeders

**Context:** implemented `docs/07_EXECUTION_PLAN.md` Phase 1.1–1.6 against `docs/03_DATABASE_SCHEMA.md` — all 34 tables, one Sequelize model per table with associations, and idempotent seeders. Verified against the real local `sams_academy` (dev) and `sams_academy_test` (test) MySQL databases, not just read for correctness.

1. **`.cjs` migrations/seeders confirmed necessary, as Phase 0 flagged.** Both `server/src/db/migrations/*.cjs` and `server/src/db/seeders/*.cjs` are plain CommonJS (`module.exports = { up, down }`), verified empirically by actually running `sequelize-cli db:migrate`/`db:seed:all` against the live dev DB — sequelize-cli's file loader `require()`s these directly regardless of `server/package.json`'s `"type": "module"`, same root cause as `.sequelizerc`/`config.cjs` from Phase 0.
2. **Migrations + models generated from one canonical schema spec, not hand-written per file.** Given 34 tables with heavy structural repetition (id/timestamps boilerplate, FK/index wiring), I transcribed `03_DATABASE_SCHEMA.md`'s DDL 1:1 into a small JS data structure (columns, indexes, FKs, timestamp shape per table) and wrote a generator that emits both the migration files and the model files from that single source of truth, so migrations and models can't drift apart. The generator itself is not part of the deliverable (scratch tooling only); the emitted `.cjs`/`.js` files in `server/src/db/migrations/` and `server/src/models/` are the real, reviewable artifacts and were spot-checked against the literal DDL (`SHOW CREATE TABLE` on `users`, `orders`, `playback_sessions`, `bank_transfer_proofs`, `settings`, `test_attempt_questions` all byte-match the doc's columns, types, defaults, constraint names, and — importantly — the doc's *omissions*: e.g. `playback_sessions.lecture_id`/`device_id` and `test_attempt_questions.selected_option_id` are deliberately left without FK constraints in the literal DDL, and the generated migrations correctly do not add constraints sequelize-cli would otherwise default to).
3. **`models/index.js` auto-loader: standard sequelize-cli-generated pattern, adapted for ESM.** Each model file default-exports `(sequelize) => Model` and defines a static `associate(models)` (sequelize-cli's own convention) instead of centralizing all association wiring in `index.js` itself. `server/src/models/index.js` dynamically `import()`s every `*.js` file in the directory (via `pathToFileURL`, since Node's ESM loader — unlike CommonJS `require()` — rejects bare Windows absolute paths), initializes each model against the shared `sequelize` singleton from `src/db/sequelize.js`, then calls every model's `associate(models)` only after all 34 are loaded, so association definitions can reference any other model regardless of file iteration order.
4. **Real bug found + fixed: Sequelize association `foreignKey` must be the camelCase model *attribute* name, not the raw snake_case DB column.** Initially every `belongsTo`/`hasMany`/`hasOne` call used the literal DDL column name (e.g. `foreignKey: 'user_id'`), matching the schema doc's own naming. This is wrong for a model using `underscored: true`: passing the snake_case string causes Sequelize to silently create a **second, colliding attribute** literally named `user_id` (distinct from the real `userId` attribute the column definition already produces), which breaks the generated `getX()`/`setX()` mixins — confirmed via an isolated repro (`B.belongsTo(A, { foreignKey: 'a_id' })` produces both `aId` and `a_id` in `B.rawAttributes`) and via a failing Jest assertion (`enrollment.getUser()` returned `null`) before the fix. Fixed by using the camelCase attribute name in every association's `foreignKey`/`otherKey` (e.g. `foreignKey: 'userId'`) — the underscored→snake_case column mapping already lives on the attribute's own definition, so associations must reference it by attribute name. All 34 models were regenerated after the fix; `server/tests/models.smoke.test.js` (added this phase) exercises `user.getEnrollments()` → `.getCourse()` and `enrollment.getUser()` specifically to guard against this regressing.
5. **Association aliasing conventions** (for Phase 2+ consumers): belongsTo aliases strip a trailing `_id` from the FK column and camelCase it (`course_id` → `course`), except two columns that don't end in `_id` and got explicit aliases — `bank_transfer_proofs.reviewed_by` → `reviewer` (belongsTo) / `reviewedBankTransferProofs` (hasMany on User), and `announcements.created_by` → `creator` / `createdAnnouncements`; `audit_logs.actor_user_id` → `actor` (hasMany stays `auditLogs`). hasMany/hasOne aliases on the parent side are the pluralized/singularized child model name. `bank_transfer_proofs.order_id` is the one FK that's individually `UNIQUE`, so it's wired as `Order.hasOne(BankTransferProof, { as: 'bankTransferProof' })` rather than `hasMany`. Added one `belongsToMany` on top of the plain belongsTo/hasMany pairs: `MockExam.belongsToMany(Question, { through: MockExamQuestion, as: 'questions' })` and the reverse, since that junction table is a clean many-to-many (unlike `test_attempt_questions`, which carries per-attempt data and is intentionally left as plain hasMany/belongsTo per the brief's own example).
6. **Timestamp shape verified per table, not assumed uniform.** Despite the global `define: { underscored: true, timestamps: true }`, the literal DDL has three different timestamp shapes: `both` (created_at+updated_at, the default — no override needed), `createdOnly` (`login_events`, `one_time_tokens`, `lecture_bookmarks`, `playback_sessions`, `payment_events`, `notifications`, `audit_logs`, `question_bookmarks` — modeled with `updatedAt: false`), and `none` (`mock_exam_questions`, `test_attempt_questions`, `user_question_history`, `user_daily_stats` — modeled with `timestamps: false`). `settings` is the one outlier with `updatedOnly` (`createdAt: false`) and no surrogate `id` column at all — its `key VARCHAR(80)` is the literal primary key.
7. **Acronym-ish camelCase↔snake_case round-trip verified empirically, not assumed**, per the Phase 0 handoff's explicit ask: confirmed with a throwaway Sequelize model that `twofaEnabled↔twofa_enabled`, `twofaSecret↔twofa_secret`, `twofaBackupCodes↔twofa_backup_codes`, and `qbankSeconds↔qbank_seconds` all round-trip correctly under `underscored: true` — no `field:` overrides needed anywhere in the 34 models.
8. **Seeder idempotency: real skip-if-exists guards, not just a documented fresh-DB-only warning.** Each of the 10 seeder files (`server/src/db/seeders/2026010101000*-seed-*.cjs`, run in dependency order matching the migration grouping) checks for its own data before inserting — by unique natural key (email, slug, code, title, settings key) or by a count threshold (questions ≥ 200, faculty ≥ 3, faqs ≥ 6) — and logs `"...already present, skipping."` instead of inserting duplicates. Verified by running `npm run seed` twice back-to-back against the same seeded dev DB: the second run is a clean all-skip no-op (no errors, no duplicate rows). sequelize-cli's `db:seed:all` does **not** maintain its own tracking table (verified: no `SequelizeData` table exists after seeding) — idempotency here is entirely these per-file guards, which is also why they matter rather than being optional polish. `seed:undo` (via `sequelize-cli db:seed:undo:all`, wired as `npm run seed:undo` in both `server/package.json` and the root `package.json`) removes seeded rows by the same natural keys.

## 2026-07-31 — Phase 2.8 security-auditor pass: 1 HIGH + 2 Medium + 2 Low fixed

**Context:** the security-auditor sub-agent ran against Phase 2's auth/device code and found 1 HIGH (phase-blocking), 2 Medium, 2 Low/cheap items, plus one informational item and two explicitly-skipped items (`login_events.email_tried` missing an index — scaling only, not exploitable; 2 wasted entropy bits in backup-code generation — still ~32 bits, rate-limited). This entry covers the HIGH/Medium/Low fixes and the judgment calls behind them.

1. **Finding 1 (HIGH) — device-cap bypass via UA fingerprint collision, fixed as a slot-takeover, not a capacity/enumeration fix.** `deviceService.matchDevice()` previously reused an existing `user_devices` row purely on `sha256(User-Agent+Accept-Language)` whenever no `device_token` cookie was presented, with **no signal distinguishing "cookie merely cleared on the same device" from "different device, same common fingerprint."** The auditor proved this lets an unrelated second/third login on a common UA/OS/locale combo (e.g. Windows+Chrome+en-US) silently reuse another session's device slot — no `DEVICE_LIMIT_REACHED`, no suspicious-login gate, and the **first session's refresh token stayed valid**, giving unlimited concurrent sessions per "slot."
   - `matchDevice()` now returns `isFingerprintOnlyMatch: Boolean(device) && !matchedByCookie` alongside the existing `isNewCandidate`, distinguishing three resolution states: (a) cookie hash matches an active row → verified same session, no special handling; (b) no cookie match but fingerprint matches an active row → **unverified** match, flagged; (c) no match at all → brand-new candidate (unchanged, still subject to the device cap).
   - **Judgment call — suspicious-login gate:** `authService.detectSuspicious()` previously only pushed `'new_device'` when `isNewCandidate` was true, which meant a fingerprint-only match was silently exempted from the reverify gate entirely (the actual root cause of "no suspicious-login gate" in the finding). Removed that exemption: `isFingerprintOnlyMatch` now also pushes a reason (`'device_takeover'`) into `detectSuspicious`'s result, so this path always requires email reverification before completing, identical treatment to a genuinely brand-new device. No carve-out was kept for "well, it's probably just a cleared cookie" — per the finding's own reasoning, the invariant that matters is "at most one live session per device slot," and reverify is cheap (the device's owner already has to have email access either way), so treating both cases identically is the safer default and avoids a second, parallel exemption.
   - **Judgment call — takeover mechanism:** `deviceService.finalizeDevice()` now revokes every currently-valid `refresh_tokens` row tied to that `device_id` (`WHERE deviceId = row.id AND revokedAt IS NULL`) whenever `isFingerprintOnlyMatch` is true, *before* the new session's refresh token is created — mirrors the existing device-token-rotation-on-every-completion behavior already documented in the Phase 2 entry above (point 3: "two independent logins that resolve to the same device slot... invalidate each other's device_token cookie... by design"), just extended to also invalidate the *refresh* token, which is the actual authentication artifact that mattered here. This does NOT increase the device cap check — it's a takeover of an *existing* row, not creation of a new one, so `assertDeviceCapacity` behavior for this path is unchanged (no-op for non-new candidates).
   - Deliberately did NOT extend `maybeSendNewDeviceAlert()`'s "new device" email to fire on `isFingerprintOnlyMatch` too (it still only fires for `isNewCandidate`). Not required by the finding, and since a takeover now always routes through the reverify-code email anyway, the account owner already gets a signal via that channel; expanding the separate "new device" alert email was judged out of scope for this pass rather than silently bundled in.
   - **Test/behavior fallout (expected, not a regression):** several pre-existing Phase 2 tests (`twofa.test.js`'s TOTP-happy-path and backup-code tests, `session.test.js`'s change-password test, `passwordReset.test.js`'s reset-password test) relied on the *old*, now-fixed shortcut — a fresh cookie-less `request(app)` call sharing a UA string with an already-registered device was completing directly instead of requiring reverify. Since that shortcut is the literal vulnerability, these tests were updated to reuse the already-authenticated `agent` (which carries the real `device_token` cookie) instead of a fresh cookie-less request, which is what each of those tests actually intends to exercise (2FA/password behavior on a known device, not device-matching semantics). No test was weakened to work around the fix; each was pointed at the right fixture.
   - New test: `server/tests/auth/login.test.js` — "two cookie-less logins with an identical UA fingerprint → second takes over the slot, revoking the first session." Asserts the second login succeeds (via the mandatory login→reverify flow, since it's now correctly flagged suspicious), the first session's raw refresh token is rejected by `/auth/refresh` afterward (`401 UNAUTHENTICATED`), and exactly one active `user_devices` row exists for the pair (slot reused, not duplicated). The pre-existing distinct-UA 3-device-cap test is untouched and still passes (different, still-valid scenario: it never presents no-cookie + colliding fingerprint).

2. **Finding 2 (Medium) — login timing side-channel, fixed with a bcrypt-cost-matched dummy compare.** `authService.js` now has a module-level `LOGIN_TIMING_PLACEHOLDER_HASH = bcrypt.hashSync('placeholder-not-a-real-password', BCRYPT_ROUNDS)`, computed once at load. ## 2026-07-31 — Phase 5.6 security-auditor pass: 1 HIGH + 1 Medium fixed (video playback)

**Context:** the security-auditor sub-agent ran against the just-built Phase 5.2/5.3 video-playback code and found 1 HIGH (blocking) + 1 Medium finding. Both fixed in this pass.

1. **Finding 1 (HIGH) — concurrent-stream lock race condition, fixed with a per-user transaction + row lock.** `videoService.acquirePlaybackSession()` previously ran an unconditional `PlaybackSession.update({endedAt: NOW()}, {where: {userId, endedAt: null}})` followed by a separate `PlaybackSession.create(...)` as two independent, unsynchronized statements — a classic read-then-write race. Concurrent `/play` calls for the same user could each observe "no active row yet" and race past each other's UPDATE before any of them INSERTed, leaving more than one `ended_at IS NULL` row at once and defeating the single-concurrent-stream anti-sharing control.
   - **Reproduced live before fixing**, exactly per the task's instructions: temporarily reverted `acquirePlaybackSession()` to the pre-fix two-statement version and ran the new concurrency test (`server/tests/student/video/streamLockConcurrency.test.js`, 15 genuinely concurrent `Promise.all`-fired `/play` calls for one authenticated, enrolled user) against it. Result: **4 simultaneously-active (`ended_at IS NULL`) sessions out of 15 concurrent requests** in that run (the exact count is nondeterministic run-to-run by nature of the race — the auditor's own reproduction saw up to 15; this run's 4 was still a clear, unambiguous violation of the "at most one active session" invariant). Confirms the race is real and reproducible, not cosmetic.
   - **Fix chosen — `sequelize.transaction()` + a row lock on the SAME user's `users` row** (`User.findByPk(userId, {transaction, lock: transaction.LOCK.UPDATE})`) taken *before* the update+create pair, all inside one transaction. This was the auditor's own suggested pattern and was implemented as-is rather than an alternative (e.g. a dedicated single-row-per-user lock table): it needs no new migration (`users` rows already exist 1:1 with the `userId` being locked), it's a standard InnoDB idiom already familiar from this codebase's other `sequelize.transaction()` call sites (`adminContentService.js`, `adminCourseService.js`, `authService.js`), and it gives exactly the required property — concurrent `acquirePlaybackSession()` calls for the SAME user serialize on that row lock (each transaction blocks until the previous one commits), while calls for DIFFERENT users lock different rows and stay fully concurrent (no cross-user contention/throughput regression).
   - **Concurrency-test approach:** `server/tests/student/video/streamLockConcurrency.test.js` fires 15 real concurrent `GET /play` requests (`Promise.all` over supertest calls created together, not sequential `await`s — the pre-existing `streamLock.test.js` suite is entirely sequential, which is exactly why it never caught this) for one authenticated, enrolled student, then asserts (a) every individual request still succeeds (the fix serializes, it doesn't reject callers), (b) exactly `CONCURRENT_REQUESTS` (15) `playback_sessions` rows were created (none lost), and (c) **exactly one** of them has `ended_at IS NULL` afterward.
