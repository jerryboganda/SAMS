## 2026-07-31 — Phase 0 bootstrap (devops-docs)

**Context:** stood up `server/` per `docs/02_ARCHITECTURE.md §2`, root tooling, and the client's test/lint wiring (`docs/07_EXECUTION_PLAN.md` Phase 0.1–0.6).

1. **Root `package.json`: `concurrently`, not npm workspaces.** `client/` and `server/` each keep their own independent `package.json`/`node_modules`/lockfile, orchestrated from the root via `concurrently` (dev) and `--prefix` (build/migrate/seed/lint/test). Chosen over npm workspaces because: (a) `client/` is a finished, externally-exported deliverable (Google AI Studio output, see the kickoff entry above) whose dependency tree (React 19, Vite 6, Tailwind 4) should stay fully isolated from the server's (Express 4, Sequelize 6, CommonJS-ish tooling) — a shared workspace root `node_modules` risks silent hoisting/version-resolution surprises across two very different stacks; (b) Hostinger's Node-app deploy model runs `npm run build` then `npm start` from the repo root with a single `package.json` contract — `--prefix`-based scripts satisfy that with zero extra tooling; (c) workspaces would force a single top-level lockfile mixing both stacks' transitive deps, complicating the Phase 14 `deploy.zip` builder (which must ship `server/node_modules` — production deps only — but never `client/node_modules`, since the client only ships its built `dist/`).
2. **Server language: ES modules JS, confirmed.** Per `CLAUDE.md §1a`/`§4` ("pick one at Phase 0 and stay consistent" — already decided as ES modules JS for the server). `server/package.json` sets `"type": "module"`; all `server/src/**/*.js` use `import`/`export`. The one deliberate exception: `server/.sequelizerc` and `server/src/db/config.cjs` are plain CommonJS (`.cjs` extension / `require`/`module.exports`), because `sequelize-cli` loads both via a raw `require()` call that cannot load ESM synchronously — `.cjs` sidesteps the package's `"type": "module"` regardless of file location. Verified empirically: `npx sequelize-cli db:migrate --env test` from `server/` correctly loads `src\db\config.cjs` and reaches a real `ECONNREFUSED 127.0.0.1:3306` (i.e. fails only on "no MySQL running", not on config loading) — confirming the `.sequelizerc` → `.cjs` config path works under `"type": "module"`. Phase 1's actual migration/seeder files will need the same `.cjs` treatment (or an equivalent ESM-compatible sequelize-cli version) — flagged here so Phase 1 doesn't rediscover this.
3. **Node version: target 20, local machine has 25.** `CLAUDE.md` and Hostinger both require Node 20 LTS, but this dev machine only has Node v25.6.1 installed (no Node 20 available locally). Both `package.json` files declare `"engines": {"node": ">=20"}` (not a hard pin to `20.x`, which would fail the local engine check and block `npm install`/`npm run verify` entirely here). All Phase 0 verification in this session therefore ran on Node 25, not Node 20. Accepted as a dev-environment note per the brief; **actually verifying green on Node 20 itself is a Phase 14 follow-up**, not done now.
4. **`npm run package` is a Phase-14 stub.** Root script `"package": "echo \"TODO: Phase 14 deploy.zip builder\" && exit 1"` — intentionally fails (exit 1) rather than silently no-op, so nothing downstream mistakes "the command exists" for "the command works." The real `deploy.zip` builder (per `docs/09_DEPLOYMENT_HOSTINGER.md`) is built in Phase 14.3.
5. **Sequelize naming strategy: `underscored: true` globally.** `docs/03_DATABASE_SCHEMA.md` specifies snake_case columns throughout (`created_at`, `updated_at`, `user_id`, ...). `server/src/db/sequelize.js` sets `define: { underscored: true, timestamps: true }` on the shared Sequelize instance (mirrored in `server/src/db/config.cjs` for sequelize-cli), so Phase 1 models can declare idiomatic camelCase JS attributes (`createdAt`, `userId`) and get the spec's snake_case columns automatically, instead of every model manually specifying `field: 'snake_case_name'` or fighting Sequelize's default camelCase-column behavior.
6. **`storage/` `.gitkeep` handling.** `.gitignore` was extended (not duplicated) so `storage/{uploads,invoices,backups,logs}/*` content stays ignored while each folder's `.gitkeep` is explicitly un-ignored (`!storage/uploads/.gitkeep` etc.) — the five `storage/` subfolders now exist in the repo structure without ever accidentally committing generated content. `storage/dev-assets/` was left un-ignored (its `.gitkeep` is a plain tracked file) since a future phase (5.1, mock video driver) may commit a small sample HLS/mp4 fixture there.
7. **Client test runner: `vitest.config.ts` reuses `vite.config.ts`'s `resolve.alias`** (by invoking the exported config function the same way Vite itself does at build time) rather than redeclaring the `@` alias a second time, so the two configs can't drift. `test.passWithNoTests: true` is set deliberately — Phase 0 wires the runner with zero test files yet, and `npm run verify` needs `client`'s `npm test` to exit 0 in that state; Phase 3+ adding real vitest specs makes this option irrelevant but harmless.

## 2026-07-31 — Phase 1 database (db-engineer): migrations, models, seeders

**Context:** implemented `docs/07_EXECUTION_PLAN.md` Phase 1.1–1.6 against `docs/03_DATABASE_SCHEMA.md` — all 34 tables, one Sequelize model per table with associations, and idempotent seeders. Verified against the real local `sams_academy` (dev) and `sams_academy_test` (test) MySQL databases, not just read for correctness.

1. **`.cjs` migrations/seeders confirmed necessary, as Phase 0 flagged.** Both `server/src/db/migrations/*.cjs` and `server/src/db/seeders/*.cjs` are plain CommonJS (`module.exports = { up, down }`), verified empirically by actually running `sequelize-cli db:migrate`/`db:seed:all` against the live dev DB — sequelize-cli's file loader `require()`s these directly regardless of `server/package.json`'s `"type": "module"`, same root cause as `.sequelizerc`/`config.cjs` from Phase 0.
2. **Migrations + models generated from one canonical schema spec, not hand-written per file.** Given 34 tables with heavy structural repetition (id/timestamps boilerplate, FK/index wiring), I transcribed `03_DATABASE_SCHEMA.md`'s DDL 1:1 into a small JS data structure (columns, indexes, FKs, timestamp shape per table) and wrote a generator that emits both the migration files and the model files from that single source of truth, so migrations and models can't drift apart. The generator itself is not part of the deliverable (scratch tooling only); the emitted `.cjs`/`.js` files in `server/src/db/migrations/` and `server/src/models/` are the real, reviewable artifacts and were spot-checked against the literal DDL (`SHOW CREATE TABLE` on `users`, `orders`, `playback_sessions`, `bank_transfer_proofs`, `settings`, `test_attempt_questions` all byte-match the doc's columns, types, defaults, constraint names, and — importantly — the doc's *omissions*: e.g. `playback_sessions.lecture_id`/`device_id` and `test_attempt_questions.selected_option_id` are deliberately left without FK constraints in the literal DDL, and the generated migrations correctly do not add constraints sequelize-cli would otherwise default to).
3. **`models/index.js` auto-loader: standard sequelize-cli-generated pattern, adapted for ESM.** Each model file default-exports `(sequelize) => Model` and defines a static `associate(models)` (sequelize-cli's own convention) instead of centralizing all association wiring in `index.js` itself. `server/src/models/index.js` dynamically `import()`s every `*.js` file in the directory (via `pathToFileURL`, since Node's ESM loader — unlike CommonJS `require()` — rejects bare Windows absolute paths), initializes each model against the shared `sequelize` singleton from `src/db/sequelize.js`, then calls every model's `associate(models)` only after all 34 are loaded, so association definitions can reference any other model regardless of file iteration order.
4. **Real bug found + fixed: Sequelize association `foreignKey` must be the camelCase model *attribute* name, not the raw snake_case DB column.** Initially every `belongsTo`/`hasMany`/`hasOne` call used the literal DDL column name (e.g. `foreignKey: 'user_id'`), matching the schema doc's own naming. This is wrong for a model using `underscored: true`: passing the snake_case string causes Sequelize to silently create a **second, colliding attribute** literally named `user_id` (distinct from the real `userId` attribute the column definition already produces), which breaks the generated `getX()`/`setX()` mixins — confirmed via an isolated repro (`B.belongsTo(A, { foreignKey: 'a_id' })` produces both `aId` and `a_id` in `B.rawAttributes`) and via a failing Jest assertion (`enrollment.getUser()` returned `null`) before the fix. Fixed by using the camelCase attribute name in every association's `foreignKey`/`otherKey` (e.g. `foreignKey: 'userId'`) — the underscored→snake_case column mapping already lives on the attribute's own definition, so associations must reference it by attribute name. All 34 models were regenerated after the fix; `server/tests/models.smoke.test.js` (added this phase) exercises `user.getEnrollments()` → `.getCourse()` and `enrollment.getUser()` specifically to guard against this regressing.
5. **Association aliasing conventions** (for Phase 2+ consumers): belongsTo aliases strip a trailing `_id` from the FK column and camelCase it (`course_id` → `course`), except two columns that don't end in `_id` and got explicit aliases — `bank_transfer_proofs.reviewed_by` → `reviewer` (belongsTo) / `reviewedBankTransferProofs` (hasMany on User), and `announcements.created_by` → `creator` / `createdAnnouncements`; `audit_logs.actor_user_id` → `actor` (hasMany stays `auditLogs`). hasMany/hasOne aliases on the parent side are the pluralized/singularized child model name. `bank_transfer_proofs.order_id` is the one FK that's individually `UNIQUE`, so it's wired as `Order.hasOne(BankTransferProof, { as: 'bankTransferProof' })` rather than `hasMany`. Added one `belongsToMany` on top of the plain belongsTo/hasMany pairs: `MockExam.belongsToMany(Question, { through: MockExamQuestion, as: 'questions' })` and the reverse, since that junction table is a clean many-to-many (unlike `test_attempt_questions`, which carries per-attempt data and is intentionally left as plain hasMany/belongsTo per the brief's own example).
6. **Timestamp shape verified per table, not assumed uniform.** Despite the global `define: { underscored: true, timestamps: true }`, the literal DDL has three different timestamp shapes: `both` (created_at+updated_at, the default — no override needed), `createdOnly` (`login_events`, `one_time_tokens`, `lecture_bookmarks`, `playback_sessions`, `payment_events`, `notifications`, `audit_logs`, `question_bookmarks` — modeled with `updatedAt: false`), and `none` (`mock_exam_questions`, `test_attempt_questions`, `user_question_history`, `user_daily_stats` — modeled with `timestamps: false`). `settings` is the one outlier with `updatedOnly` (`createdAt: false`) and no surrogate `id` column at all — its `key VARCHAR(80)` is the literal primary key.
7. **Acronym-ish camelCase↔snake_case round-trip verified empirically, not assumed**, per the Phase 0 handoff's explicit ask: confirmed with a throwaway Sequelize model that `twofaEnabled↔twofa_enabled`, `twofaSecret↔twofa_secret`, `twofaBackupCodes↔twofa_backup_codes`, and `qbankSeconds↔qbank_seconds` all round-trip correctly under `underscored: true` — no `field:` overrides needed anywhere in the 34 models.
8. **Seeder idempotency: real skip-if-exists guards, not just a documented fresh-DB-only warning.** Each of the 10 seeder files (`server/src/db/seeders/2026010101000*-seed-*.cjs`, run in dependency order matching the migration grouping) checks for its own data before inserting — by unique natural key (email, slug, code, title, settings key) or by a count threshold (questions ≥ 200, faculty ≥ 3, faqs ≥ 6) — and logs `"...already present, skipping."` instead of inserting duplicates. Verified by running `npm run seed` twice back-to-back against the same seeded dev DB: the second run is a clean all-skip no-op (no errors, no duplicate rows). sequelize-cli's `db:seed:all` does **not** maintain its own tracking table (verified: no `SequelizeData` table exists after seeding) — idempotency here is entirely these per-file guards, which is also why they matter rather than being optional polish. `seed:undo` (via `sequelize-cli db:seed:undo:all`, wired as `npm run seed:undo` in both `server/package.json` and the root `package.json`) removes seeded rows by the same natural keys.
9. **Seed data specifics not fully spelled out by `03_DATABASE_SCHEMA.md`, resolved as follows:** (a) all 200 seeded questions use `exam_category = 'NRE1'` uniformly (matching the one seeded course/mock exam) rather than spreading across all 8 exam categories — the doc only asks for spread across subjects/systems/difficulties, and keeping one exam category keeps later QBank-meta/enrollment-scoped counts self-consistent; (b) question stems/explanations are generated from a small set of clinical-vignette-style templates parameterized by subject+system+case-number (see `20260101010003-seed-04-questions.cjs`) — templated but non-lorem-ipsum and structurally distinct per question, per the brief; (c) the mock exam's 50 questions are the first 50 seeded questions by id (deterministic, not random); (d) settings keys used for legal pages: `legal.privacy`, `legal.terms`, `legal.refund`, `site.about`, each a JSON object `{ title, content }` with clearly-labeled placeholder text ("replace with final legal copy before go-live") — no other settings keys were added (e.g. no payment/bank-detail settings yet — out of Phase 1 scope, deferred to Phase 9); (e) demo activity is 5 completed `practice`-mode test sessions (10 questions each, one per day for the last 5 days) with a deterministic PRNG (fixed seed, so re-running against a truly fresh DB reproduces the same numbers) targeting ~70% correct / 20% incorrect / 10% skipped per session; `user_question_history` and `user_daily_stats` are also populated from the same sessions (beyond what the brief's seed list explicitly named) since both tables exist specifically to power the analytics/dashboard screens the brief says this data is for — `questions.times_attempted`/`times_correct` were deliberately **not** touched, since the schema doc marks them "denormalized, cron-refreshed" (Phase 8.1's job), so 0 is the correct pre-cron seed state.
10. **Verification performed for real, not assumed:** `npm run migrate` (34/34 tables) → `npm run migrate:undo:all` (34/34 clean revert) → `npm run migrate` again (34/34 clean re-apply) against the live dev DB; `NODE_ENV=test npx sequelize-cli db:migrate --env test` against the live test DB (34/34 clean); `npm run seed` twice back-to-back (insert-then-skip, verified via `SELECT COUNT(*)`/integrity queries through the real `mysql.exe` CLI — every question has exactly 4 options and exactly 1 correct option); `server/tests/models.smoke.test.js` (new) exercises real model associations against a freshly-`globalSetup`-migrated test DB; root `npm run verify` (lint+test+build across server and client) is green with 0 lint errors (server: 0 warnings after the no-op-associate cleanup in point 4; client's pre-existing warnings are untouched, out of Phase 1 scope).
