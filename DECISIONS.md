## 2026-07-31 — Phase 1 database (db-engineer): migrations, models, seeders

**Context:** implemented `docs/07_EXECUTION_PLAN.md` Phase 1.1–1.6 against `docs/03_DATABASE_SCHEMA.md` — all 34 tables, one Sequelize model per table with associations, and idempotent seeders. Verified against the real local `sams_academy` (dev) and `sams_academy_test` (test) MySQL databases, not just read for correctness.

1. **`.cjs` migrations/seeders confirmed necessary, as Phase 0 flagged.** Both `server/src/db/migrations/*.cjs` and `server/src/db/seeders/*.cjs` are plain CommonJS (`module.exports = { up, down }`), verified empirically by actually running `sequelize-cli db:migrate`/`db:seed:all` against the live dev DB — sequelize-cli's file loader `require()`s these directly regardless of `server/package.json`'s `"type": "module"`, same root cause as `.sequelizerc`/`config.cjs` from Phase 0.
2. **Migrations + models generated from one canonical schema spec, not hand-written per file.** Given 34 tables with heavy structural repetition (id/timestamps boilerplate, FK/index wiring), I transcribed `03_DATABASE_SCHEMA.md`'s DDL 1:1 into a small JS data structure (columns, indexes, FKs, timestamp shape per table) and wrote a generator that emits both the migration files and the model files from that single source of truth, so migrations and models can't drift apart. The generator itself is not part of the deliverable (scratch tooling only); the emitted `.cjs`/`.js` files in `server/src/db/migrations/` and `server/src/models/` are the real, reviewable artifacts and were spot-checked against the literal DDL (`SHOW CREATE TABLE` on `users`, `orders`, `playback_sessions`, `bank_transfer_proofs`, `settings`, `test_attempt_questions` all byte-match the doc's columns, types, defaults, constraint names, and — importantly — the doc's *omissions*: e.g. `playback_sessions.lecture_id`/`device_id` and `test_attempt_questions.selected_option_id` are deliberately left without FK constraints in the literal DDL, and the generated migrations correctly do not add constraints sequelize-cli would otherwise default to).
3. **`models/index.js` auto-loader: standard sequelize-cli-generated pattern, adapted for ESM.** Each model file default-exports `(sequelize) => Model` and defines a static `associate(models)` (sequelize-cli's own convention) instead of centralizing all association wiring in `index.js` itself. `server/src/models/index.js` dynamically `import()`s every `*.js` file in the directory (via `pathToFileURL`, since Node's ESM loader — unlike CommonJS `require()` — rejects bare Windows absolute paths), initializes each model against the shared `sequelize` singleton from `src/db/sequelize.js`, then calls every model's `associate(models)` only after all 34 are loaded, so association definitions can reference any other model regardless of file iteration order.
4. **Real bug found + fixed: Sequelize association `foreignKey` must be the camelCase model *attribute* name, not the raw snake_case DB column.** Initially every `belongsTo`/`hasMany`/`hasOne` call used the literal DDL column name (e.g. `foreignKey: 'user_id'`), matching the schema doc's own naming. This is wrong for a model using `underscored: true`: passing the snake_case string causes Sequelize to silently create a **second, colliding attribute** literally named `user_id` (distinct from the real `userId` attribute the column definition already produces), which breaks the generated `getX()`/`setX()` mixins — confirmed via an isolated repro (`B.belongsTo(A, { foreignKey: 'a_id' })` produces both `aId` and `a_id` in `B.rawAttributes`) and via a failing Jest assertion (`enrollment.getUser()` returned `null`) before the fix. Fixed by using the camelCase attribute name in every association's `foreignKey`/`otherKey` (e.g. `foreignKey: 'userId'`) — the underscored→snake_case column mapping already lives on the attribute's own definition, so associations must reference it by attribute name. All 34 models were regenerated after the fix; `server/tests/models.smoke.test.js` (added this phase) exercises `user.getEnrollments()` → `.getCourse()` and `enrollment.getUser()` specifically to guard against this regressing.
5. **Association aliasing conventions** (for Phase 2+ consumers): belongsTo aliases strip a trailing `_id` from the FK column and camelCase it (`course_id` → `course`), except two columns that don't end in `_id` and got explicit aliases — `bank_transfer_proofs.reviewed_by` → `reviewer` (belongsTo) / `reviewedBankTransferProofs` (hasMany on User), and `announcements.created_by` → `creator` / `createdAnnouncements`; `audit_logs.actor_user_id` → `actor` (hasMany stays `auditLogs`). hasMany/hasOne aliases on the parent side are the pluralized/singularized child model name. `bank_transfer_proofs.order_id` is the one FK that's individually `UNIQUE`, so it's wired as `Order.hasOne(BankTransferProof, { as: 'bankTransferProof' })` rather than `hasMany`. Added one `belongsToMany` on top of the plain belongsTo/hasMany pairs: `MockExam.belongsToMany(Question, { through: MockExamQuestion, as: 'questions' })` and the reverse, since that junction table is a clean many-to-many (unlike `test_attempt_questions`, which carries per-attempt data and is intentionally left as plain hasMany/belongsTo per the brief's own example).
6. **Timestamp shape verified per table, not assumed uniform.** Despite the global `define: { underscored: true, timestamps: true }`, the literal DDL has three different timestamp shapes: `both` (created_at+updated_at, the default — no override needed), `createdOnly` (`login_events`, `one_time_tokens`, `lecture_bookmarks`, `playback_sessions`, `payment_events`, `notifications`, `audit_logs`, `question_bookmarks` — modeled with `updatedAt: false`), and `none` (`mock_exam_questions`, `test_attempt_questions`, `user_question_history`, `user_daily_stats` — modeled with `timestamps: false`). `settings` is the one outlier with `updatedOnly` (`createdAt: false`) and no surrogate `id` column at all — its `key VARCHAR(80)` is the literal primary key.
7. **Acronym-ish camelCase↔snake_case round-trip verified empirically, not assumed**, per the Phase 0 handoff's explicit ask: confirmed with a throwaway Sequelize model that `twofaEnabled↔twofa_enabled`, `twofaSecret↔twofa_secret`, `twofaBackupCodes↔twofa_backup_codes`, and `qbankSeconds↔qbank_seconds` all round-trip correctly under `underscored: true` — no `field:` overrides needed anywhere in the 34 models.
8. **Seeder idempotency: real skip-if-exists guards, not just a documented fresh-DB-only warning.** Each of the 10 seeder files (`server/src/db/seeders/2026010101000*-seed-*.cjs`, run in dependency order matching the migration grouping) checks for its own data before inserting — by unique natural key (email, slug, code, title, settings key) or by a count threshold (questions ≥ 200, faculty ≥ 3, faqs ≥ 6) — and logs `"...already present, skipping."` instead of inserting duplicates. Verified by running `npm run seed` twice back-to-back against the same seeded dev DB: the second run is a clean all-skip no-op (no errors, no duplicate rows). sequelize-cli's `db:seed:all` does **not** maintain its own tracking table (verified: no `SequelizeData` table exists after seeding) — idempotency here is entirely these per-file guards, which is also why they matter rather than being optional polish. `seed:undo` (via `sequelize-cli db:seed:undo:all`, wired as `npm run seed:undo` in both `server/package.json` and the root `package.json`) removes seeded rows by the same natural keys.

## 2026-07-31 — Phase 2.8 security-auditor pass: 1 HIGH + 2 Medium + 2 Low fixed

**Context:** the security-auditor sub-agent ran against Phase 2's auth/device code and found 1 HIGH (phase-blocking), 2 Medium, 2 Low/cheap items, plus one informational item and two explicitly-skipped items (`login_events.email_tried` missing an index — scaling only, not exploitable; 2 wasted entropy bits in backup-code generation — still ~32 bits, rate-limited). This entry covers the HIGH/Medium/Low fixes and the judgment calls behind them.

1. **Finding 1 (HIGH) — device-cap bypass via UA fingerprint collision, fixed as a slot-takeover, not a capacity/enumeration fix.** `deviceService.matchDevice()` previously reused an existing `user_devices` row purely on `sha256(User-Agent+Accept-Language)` whenever no `device_token` cookie was presented, with **no signal distinguishing "cookie merely cleared on the same device" from "different device, same common fingerprint."** The auditor proved this lets an unrelated second/third login on a common UA/OS/locale combo (e.g. Windows+Chrome+en-US) silently reuse another session's device slot — no `DEVICE_LIMIT_REACHED`, no suspicious-login gate, and the **first session's refresh token stayed valid**, giving unlimited concurrent sessions per "slot."
   - `matchDevice()` now returns `isFingerprintOnlyMatch: Boolean(device) && !matchedByCookie` alongside the existing `isNewCandidate`, distinguishing three resolution states: (a) cookie hash matches an active row → verified same session, no special handling; (b) no cookie match but fingerprint matches an active row → **unverified** match, flagged; (c) no match at all → brand-new candidate (unchanged, still subject to the device cap).
   - **Judgment call — suspicious-login gate:** `authService.detectSuspicious()` previously only pushed `'new_device'` when `isNewCandidate` was true, which meant a fingerprint-only match was silently exempted from the reverify gate entirely (the actual root cause of "no suspicious-login gate" in the finding). Removed that exemption: `isFingerprintOnlyMatch` now also pushes a reason (`'device_takeover'`) into `detectSuspicious`'s result, so this path always requires email reverification before completing, identical treatment to a genuinely brand-new device. No carve-out was kept for "well, it's probably just a cleared cookie" — per the finding's own reasoning, the invariant that matters is "at most one live session per device slot," and reverify is cheap (the device's owner already has to have email access either way), so treating both cases identically is the safer default and avoids a second, parallel exemption.
   - **Judgment call — takeover mechanism:** `deviceService.finalizeDevice()` now revokes every currently-valid `refresh_tokens` row tied to that `device_id` (`WHERE deviceId = row.id AND revokedAt IS NULL`) whenever `isFingerprintOnlyMatch` is true, *before* the new session's refresh token is created — mirrors the existing device-token-rotation-on-every-completion behavior already documented in the Phase 2 entry above (point 3: "two independent logins that resolve to the same device slot... invalidate each other's device_token cookie... by design"), just extended to also invalidate the *refresh* token, which is the actual authentication artifact that mattered here. This does NOT increase the device cap check — it's a takeover of an *existing* row, not creation of a new one, so `assertDeviceCapacity` behavior for this path is unchanged (no-op for non-new candidates).
   - Deliberately did NOT extend `maybeSendNewDeviceAlert()`'s "new device" email to fire on `isFingerprintOnlyMatch` too (it still only fires for `isNewCandidate`). Not required by the finding, and since a takeover now always routes through the reverify-code email anyway, the account owner already gets a signal via that channel; expanding the separate "new device" alert email was judged out of scope for this pass rather than silently bundled in.
   - **Test/behavior fallout (expected, not a regression):** several pre-existing Phase 2 tests (`twofa.test.js`'s TOTP-happy-path and backup-code tests, `session.test.js`'s change-password test, `passwordReset.test.js`'s reset-password test) relied on the *old*, now-fixed shortcut — a fresh cookie-less `request(app)` call sharing a UA string with an already-registered device was completing directly instead of requiring reverify. Since that shortcut is the literal vulnerability, these tests were updated to reuse the already-authenticated `agent` (which carries the real `device_token` cookie) instead of a fresh cookie-less request, which is what each of those tests actually intends to exercise (2FA/password behavior on a known device, not device-matching semantics). No test was weakened to work around the fix; each was pointed at the right fixture.
   - New test: `server/tests/auth/login.test.js` — "two cookie-less logins with an identical UA fingerprint → second takes over the slot, revoking the first session." Asserts the second login succeeds (via the mandatory login→reverify flow, since it's now correctly flagged suspicious), the first session's raw refresh token is rejected by `/auth/refresh` afterward (`401 UNAUTHENTICATED`), and exactly one active `user_devices` row exists for the pair (slot reused, not duplicated). The pre-existing distinct-UA 3-device-cap test is untouched and still passes (different, still-valid scenario: it never presents no-cookie + colliding fingerprint).

2. **Finding 2 (Medium) — login timing side-channel, fixed with a bcrypt-cost-matched dummy compare.** `authService.js` now has a module-level `LOGIN_TIMING_PLACEHOLDER_HASH = bcrypt.hashSync('placeholder-not-a-real-password', BCRYPT_ROUNDS)`, computed once at load. ## 2026-07-31 — Phase 5.6 security-auditor pass: 1 HIGH + 1 Medium fixed (video playback)

1. **Finding 1 (HIGH) — concurrent-stream lock race condition, fixed with a per-user transaction + row lock.** `videoService.acquirePlaybackSession()` previously ran an unconditional `PlaybackSession.update({endedAt: NOW()}, {where: {userId, endedAt: null}})` followed by a separate `PlaybackSession.create(...)` as two independent, unsynchronized statements — a classic read-then-write race. Concurrent `/play` calls for the same user could each observe "no active row yet" and race past each other's UPDATE before any of them INSERTed, leaving more than one `ended_at IS NULL` row at once and defeating the single-concurrent-stream anti-sharing control.
   - **Reproduced live before fixing**, exactly per the task's instructions: temporarily reverted `acquirePlaybackSession()` to the pre-fix two-statement version and ran the new concurrency test (`server/tests/student/video/streamLockConcurrency.test.js`, 15 genuinely concurrent `Promise.all`-fired `/play` calls for one authenticated, enrolled user) against it. Result: **4 simultaneously-active (`ended_at IS NULL`) sessions out of 15 concurrent requests** in that run (the exact count is nondeterministic run-to-run by nature of the race — the auditor's own reproduction saw up to 15; this run's 4 was still a clear, unambiguous violation of the "at most one active session" invariant). Confirms the race is real and reproducible, not cosmetic.
   - **Fix chosen — `sequelize.transaction()` + a row lock on the SAME user's `users` row** (`User.findByPk(userId, {transaction, lock: transaction.LOCK.UPDATE})`) taken *before* the update+create pair, all inside one transaction. This was the auditor's own suggested pattern and was implemented as-is rather than an alternative (e.g. a dedicated single-row-per-user lock table): it needs no new migration (`users` rows already exist 1:1 with the `userId` being locked), it's a standard InnoDB idiom already familiar from this codebase's other `sequelize.transaction()` call sites (`adminContentService.js`, `adminCourseService.js`, `authService.js`), and it gives exactly the required property — concurrent `acquirePlaybackSession()` calls for the SAME user serialize on that row lock (each transaction blocks until the previous one commits), while calls for DIFFERENT users lock different rows and stay fully concurrent (no cross-user contention/throughput regression).

2. **Taxonomy scope (`GET /qbank/meta`): returns ALL `subjects`/`systems` rows (global taxonomy, ~9/~10 rows per the seed data), not just ones with a matching question in the user's scope.** A filter UI is more useful showing every subject with an honest `questionsCount: 0` (so the student knows it exists but has nothing filterable right now under their current access) than silently hiding it. Per-filter counts (`docs/04_API_SPEC.md` §4 "per-filter available counts") are computed as ONE grouped aggregate (`GROUP BY exam_category, subject_id, system_id`) — 7 queries total for the whole endpoint (enrollments+course join, subjects, systems, the grouped aggregate, 3 scoped pool-count aggregates), no N+1, no hard query-budget AC here unlike Phase 6.1's dashboard. Extra fields (`countsByCategory`, `filterCounts` — the raw per-(examCategory,subjectId,systemId) grouped rows) are additive-only, safe since `qbankApi.getMeta()` is typed `Promise<any>`.

3. **Pool definitions, applied identically in `GET /qbank/meta`'s counts AND `POST /qbank/tests`'s pool resolution (one shared reading, not two divergent ones):** `unused` = active, in-scope questions with no `user_question_history` row for this user OR `times_seen=0`; `incorrect` = `last_result='incorrect'` **only** (the schema's own field for exactly "the most recent attempt was wrong" — a question answered wrong once then later correctly has its `last_result` overwritten to `'correct'` by the same upsert `finalizeCompleted`/`finalizeAbandoned` use, so it naturally and automatically drops out of the incorrect pool with no extra bookkeeping); `bookmarked` = a `question_bookmarks` row for this user. All three scoped to the user's accessible exam categories (active, non-expired, `courses.includes_qbank=true` enrollments — same active-and-unexpired gate as `services/videoService.js#assertEnrolled`, reimplemented locally as `getAccessibleExamCategories()` rather than cross-imported, same "different concern" reasoning as Phase 6's `assertEnrolledInCourse`) and `questions.is_active=true`.

4. **`count` validation: rejected with 422 `VALIDATION_ERROR` outside [5,200] (zod `.min(5).max(200)`), never silently clamped.** Chosen over silent clamping because a student who explicitly asks for 300 and silently gets back 200 with no explanation is worse UX than a clear validation error; the frontend's own `CreateTestPage.tsx` wizard already clamps its slider client-side to `[5, maxAvailable<=200]` before submit, so a real out-of-range request shouldn't happen in normal use anyway.

5. **Insufficient pool size: 422 `INSUFFICIENT_QUESTIONS` (`{available, requested}` in `error.details`), not "return fewer with a warning".** `GET /qbank/meta` shows live per-filter/pool counts BEFORE the create-test wizard's submit step, so an exact-count mismatch is avoidable in normal use; silently returning fewer than requested would leave a client-computed `timeLimitSeconds` (e.g. "1.2 min/question × requested count") silently wrong for the actual, smaller test that came back.

6. **`ACTIVE_TEST_EXISTS` (409): scoped per-user, platform-wide — ANY `test_sessions` row with `status='in_progress'` for this user, regardless of `exam_category`** (mirrors `docs/02_ARCHITECTURE.md` §4's one-active-playback-session-per-user philosophy, which this phase's brief explicitly asked to mirror; verified with a dedicated cross-category test). `error.details` is `{testId}` — the one piece of information a "resume or abandon?" prompt needs — chosen because it is EXACTLY the shape `client/src/pages/student/CreateTestPage.tsx` already reads (`err.details?.testId`) and `client/src/api/endpoints/qbank.ts`'s own mock driver already throws, confirmed by reading both before landing this.

7. **`forceNew` (body field): not in `docs/04_API_SPEC.md`'s literal shorthand, but implemented anyway — it's a real, already-wired frontend field.** `CreateTestRequest.forceNew` is sent by `CreateTestPage.tsx`'s "Abandon & Start New Block" button in its `ACTIVE_TEST_EXISTS` conflict modal; per CLAUDE.md §1a, an already-built, already-live frontend behavior wins over the doc's shorthand list. When `forceNew===true` and an in-progress session exists, it is abandoned first (identical `finalizeAbandoned()` path `POST /abandon` uses — answers so far are still recorded to history) and a fresh test is created normally; `forceNew` defaults to `false`, preserving the literal-spec 409 behavior when omitted.

8. **Answer secrecy (the security-critical core), exact rules implemented:** exam/mock mode + `status==='in_progress'` → `is_correct`/`explanation` (and `reference_text`, see point 9) are omitted from **every** question, answered or not — no exceptions. Practice mode + `status==='in_progress'` → included **only** for a question with `answered_at IS NOT NULL`, still hidden for untouched ones. **Once `status !== 'in_progress'` (i.e. `completed` OR `abandoned`), secrecy fully lifts for every mode, on both `GET /qbank/tests/:id` and `GET /qbank/tests/:id/review`.** The API spec's literal wording only names "until completed", but `abandoned` is just as terminal — `PATCH /answer` rejects any non-`in_progress` session so there is no path back to "still gameable" once abandoned — and the review endpoint's OWN spec explicitly unlocks on either `completed` or `abandoned`; gating the session-state GET differently from review would be an indefensible split for the same underlying "is this test still live" question. Implementation: secret fields are set to JS `undefined` (never `null`) so `res.json()`'s `JSON.stringify` drops the KEY entirely — proven, not just asserted, by a recursive `findForbiddenKeys()` scanner (`server/tests/helpers/leakScan.js`) walking the actual parsed response body for `isCorrect`/`is_correct`/`explanation` anywhere in the tree, for both an untouched AND a just-answered exam-mode question in the same test.

9. **`reference_text` is given the exact same secrecy gating as `explanation`**, even though `docs/04_API_SPEC.md`'s wording only names "`is_correct` and `explanation`" — the review endpoint's own payload description lists them side by side ("explanation, reference_text") as the post-completion reveal, and `reference_text` is equally answer-revealing content (often names the diagnosis/mechanism directly). Hiding one but not the other would be a real, exploitable leak.

10. **Auto-submit: lazy, on-access enforcement (no cron in this phase), one shared scoring/finalize function.** `autoFinalizeIfExpired(session)` is called at the top of `GET /qbank/tests/:id`, `PATCH .../answer`, `POST .../submit`, and `POST .../abandon` — a no-op unless the session is `in_progress`, timed, and past `started_at + time_limit_seconds`; when it fires it runs the exact same `finalizeCompleted()` a manual submit uses (never a duplicated scoring path). `GET .../review` is the one exception — it deliberately does NOT auto-finalize (the brief's own enumeration names only "GET/PATCH/submit/abandon"); an expired-but-not-yet-lazily-settled session still 403s there exactly like any other in-progress session, and the very next call to any of the other four endpoints (most likely the client's own session-state poll) settles it. `PATCH /answer` distinguishes two 409s by `error.code`: `TEST_NOT_IN_PROGRESS` (session was ALREADY completed/abandoned before this call — nothing changes) vs `TEST_EXPIRED` (session WAS in_progress, this very call is what triggers the auto-submit side effect, THEN the answer itself is rejected/never recorded).

13. **Abandon vs submit — three deliberate, documented differences (`services/qbankService.js`'s `finalizeAbandoned` doc comment):** (a) `user_question_history` is upserted ONLY for questions with `answered_at IS NOT NULL` — an abandoned test's untouched questions were never engaged with and must not count as "seen" (they'd otherwise wrongly stop appearing in the "unused" pool forever). (b) `user_daily_stats` is NOT touched at all on abandon — the daily-stat bullet in the task brief is scoped to the submit endpoint only. 9. **Question-difficulty cron implementation detour, worth recording:** the natural ORM-idiomatic approach — one grouped `SELECT ... GROUP BY question_id` aggregate feeding `Question.bulkCreate(rows, { updateOnDuplicate: ['timesAttempted','timesCorrect'] })` (a single `INSERT ... ON DUPLICATE KEY UPDATE`) — was tried FIRST and empirically fails against this schema: MySQL validates an INSERT statement's NOT NULL columns (`subject_id`, `system_id`, `stem`, `explanation`, `exam_category` — none have a DB-level DEFAULT) even when every target id already exists and the statement is guaranteed to resolve to the UPDATE branch — reproduced against the real test DB (`Error: Field 'subject_id' doesn't have a default value`). Landed on a single raw, **100% static** (zero interpolated/external input at any point) `UPDATE questions q LEFT JOIN (...) agg ON ... SET ... = COALESCE(agg.x, 0)` statement via `sequelize.query()` instead — ONE query total (not the originally-planned "aggregate + bulk update" two-step), and the `LEFT JOIN ... COALESCE(...,0)` shape means a question whose attempts disappear is correctly reset to 0 in the same statement, no separate reset pass needed. ## 2026-08-01 — Phase 9.1-9.2 (integrations-dev): coupons, order creation, PaymentGateway adapter factory + `mock` driver, shared payment-success path

**Context:** `docs/07_EXECUTION_PLAN.md` 9.1 (coupon service + quote) and 9.2 (order creation + gateway factory + `mock` gateway + shared success path). Read `docs/04_API_SPEC.md` §5, `docs/02_ARCHITECTURE.md` §7, and `docs/03_DATABASE_SCHEMA.md`'s "Integrity & operational rules" in full before coding. This is explicitly foundation work — 9.3-9.6/9.5b (JazzCash/EasyPaisa/Raast/bank-transfer/PayFast/Safepay) are separate follow-up dispatches that plug into the factory and shared success path built here; every contract decision below was made with "will a future driver author be able to implement against this without guessing" in mind.

1. **`invoice_no` is assigned at order-CREATION time, not payment-success time.** `orders.invoice_no VARCHAR(30) NOT NULL UNIQUE` — the column itself can never be null, so a `pending` order must already have one the instant its row is inserted; there is no valid intermediate state where an order exists without an invoice number. `server/src/services/orderService.js#createOrder` generates it (via `generateInvoiceNo`, locked read-modify-write against `settings['invoice_seq']`) inside the SAME short transaction that inserts the `orders` row. Format `SAMS-{year}-{seq, 5-digit zero-padded}`; `seq` resets to 1 on the first invoice of a new UTC calendar year — the schema's own example (`SAMS-2026-00001`) doesn't say whether numbering is per-year or lifetime-monotonic, and per-year is the more common real-world invoicing convention, so that's what was chosen. A future admin "manual mark-paid" or refund flow never needs to touch this — it's already set.

2. **Bug found + fixed during the invoice_no concurrency test: a connection-pool self-deadlock, not a locking-correctness bug.** The lock/read-modify-write logic itself was correct from the first draft, but `generateInvoiceNo()`'s lazy row-creation helper (`ensureInvoiceSeqRowExists`, which does its own non-transactional `Setting.findByPk`/`create`) was originally *called from inside* the already-open `sequelize.transaction(...)` callback. That helper doesn't participate in the outer transaction, so it needs a SECOND pool connection while the first is still checked out — under `CONCURRENT_REQUESTS = 15` against the shared pool's `max: 10` (`server/src/db/sequelize.js`), every in-flight request ended up holding one connection and waiting on `acquire: 30000`-ms for a second, and none could ever free one up (classic pool self-deadlock, not a query-level deadlock). Reproduced exactly as `"Exceeded timeout of 30000 ms"` on the concurrency test (matching the pool's own 30 s `acquire` timeout is what gave it away). Fixed by moving `await ensureInvoiceSeqRowExists()` to run once, BEFORE `sequelize.transaction(...)` opens, in `createOrder()` — the locked read-modify-write itself (`generateInvoiceNo`, called from inside the transaction) only ever needs the ONE connection the transaction already holds. Re-ran the 15-concurrent-request test after the fix: completed in ~650-750 ms (vs. timing out at 30 000 ms before), 15 distinct sequential invoice numbers, zero collisions/gaps, verified across multiple repeated runs. This is exactly the kind of thing 9.9's "fuller race test" and 9.10's security audit should keep an eye out for in any FUTURE code that opens a transaction and then calls a helper that does its own separate (non-`{transaction}`) queries from inside that callback.

3. **The "enabled but not configured" factory contract for future gateway drivers** (`server/src/adapters/payments/index.js`'s header comment is the canonical copy — repeating the summary here per the task brief): a gateway code is available iff (a) it has a driver registered in the factory's `DRIVERS` map, AND (b) its code string appears in `env.PAYMENTS_ENABLED_GATEWAYS` (comma list), AND (c) its driver's `isConfigured()` (sync, no I/O) returns `true`. Missing (a) or (b) = "not enabled at all"; failing (c) while (a)+(b) hold = "enabled but not configured" (e.g. an admin added `payfast` to the env list without filling in `PAYFAST_MERCHANT_ID`/`PAYFAST_SECURED_KEY`). BOTH cases surface to the client as the identical `422 GATEWAY_NOT_CONFIGURED` — the distinction only matters for how a FUTURE driver author writes its own `isConfigured()`, never for what the client observes (no reason to leak which gateway codes almost exist in this build). 9.3/9.4's real drivers should implement `isConfigured()` as "are the required env vars for this gateway all non-empty"; 9.5b's PayFast/Safepay placeholder stubs should have `isConfigured()` permanently (or near-permanently) return `false` until someone actually fills the stub in with real integration code, not just real env values — a placeholder must never accidentally start accepting real traffic just because someone pasted credentials into `.env`.

4. **Money-math precision approach: string-based integer-cents conversion, never a float multiply.** Sequelize/mysql2 return `DECIMAL(10,2)` columns as JS strings (e.g. `course.price === "15000.00"`), specifically so callers don't lose precision doing float arithmetic on them — `19.99 * 100 === 1998.9999999999998` in IEEE-754 double, not the exact `1999` (verified live, used as the task's own doc-gap-style regression test in `server/tests/checkout/money.test.js` — the earlier draft of that test picked `15000.10` as its "bad" example, which turned out to round correctly by coincidence for that specific value in V8; `19.99` was substituted after actually running both in `node -e` rather than trusting the general claim without checking a concrete number). `server/src/utils/money.js`'s `toCents`/`fromCents` convert via pure string splitting (never `Number(x) * 100`), do all arithmetic on the resulting exact integers, then format back to a canonical 2-decimal string. `server/src/services/couponService.js#computeQuoteAmounts` is THE single function both `POST /checkout/quote` and `POST /checkout/orders` call (directly or via `couponService.getQuote`) so they can never compute a different discount for the same inputs — this was an explicit task requirement, not just good practice, and is asserted directly by `server/tests/checkout/orders.test.js`'s "amounts EXACTLY match" tests.

5. **Coupon validation check order** (existence/active → validity window → usage cap → course-applicability) **is a judgment call** — `docs/04_API_SPEC.md` §5 names the 4 error codes but not a precedence when more than one condition is true simultaneously (e.g. an inactive AND exhausted coupon). Chose the order above as the most natural "cheapest/most fundamental check first" reading. Also per the task brief: `docs/03_DATABASE_SCHEMA.md`'s coupons table only defines ONE "expired" code, so BOTH "not yet valid" (`now < valid_from`) and "no longer valid" (`now > valid_until`) map to `COUPON_EXPIRED` — no separate "not yet started" code exists.

6. **Coupon-exhaustion re-check at payment-success time throws and rolls back, rather than inventing a new order status.** `server/src/services/orderService.js#completeOrderPayment` re-validates `max_uses` under a row lock on the coupon (the actual race-safety mechanism `docs/07_EXECUTION_PLAN.md` 9.2's coupon-abuse AC asks for). If a concurrent order's success path already exhausted the coupon by the time this one's transaction acquires the lock, this throws `409 COUPON_EXHAUSTED`, the whole transaction rolls back, and the LOSING order is left exactly as it was (still `pending`/`awaiting_verification` — not paid, not enrolled, not flipped to some new "rejected" status the schema doesn't define). `processGatewayCallback` catches this, logs it, and the webhook/return route still responds gracefully (200 / redirect) either way — a losing coupon race must never surface as a raw error to the gateway or the browser. Verified by `server/tests/checkout/couponRedemptionRace.test.js` (2 concurrent orders, `max_uses=1` coupon, real `Promise.all` concurrency — exactly one order ends up `paid`+enrolled, `usedCount` is exactly 1, never 2).

7. **Idempotency is implemented via a row-locked order-status gate, not a uniqueness constraint on `payment_events(gateway, external_ref)`.** The task brief describes idempotency as "keyed on (gateway, external_ref)"; `docs/03_DATABASE_SCHEMA.md`'s `payment_events` table only has a plain INDEX on `(gateway, external_ref)` (`idx_pe_ext`), not a UNIQUE constraint — deliberately, since the schema wants EVERY callback (including replays and forged attempts) logged for audit, not silently rejected by a DB-level uniqueness violation. So `completeOrderPayment()` achieves the same practical guarantee a different way: it locks the target order row (`SELECT ... FOR UPDATE`) and only proceeds if the order's CURRENT status is still `pending`/`awaiting_verification` (`PAYABLE_STATUSES`); any other status (already `paid` — the ordinary replay case; or `failed`/`cancelled`/`refunded` — e.g. a stale success callback arriving after a hypothetical future admin refund-flag action) is treated as "already resolved, do nothing" and returns `alreadyProcessed: true` with zero writes. This is provably at-most-once per order regardless of how many distinct `external_ref`s a replay/attacker throws at it, which is a strictly stronger guarantee than exact-`external_ref`-match dedup alone would give. Verified by `server/tests/checkout/idempotentReplay.test.js`: same callback fired twice → 2 `payment_events` rows (both logged, per the "log every event" requirement) but exactly 1 enrollment, 1 notification, 1 coupon increment, and `paidAt` unchanged on the second call.

8. **Mock gateway's simulated redirect-flow design.** `server/src/adapters/payments/mock.js#createCheckout` mirrors a genuine hosted-checkout redirect (the same shape JazzCash/EasyPaisa/PayFast/Safepay will use): `redirectUrl` points at our OWN `GET /api/v1/checkout/return/mock`, carrying `orderId` + a signed token, rather than e.g. immediately mutating the order to `paid` inside `createCheckout` itself. `handleCallback` then genuinely VERIFIES that token (`crypto.timingSafeEqual`, never a naive `===` string compare) before ever reporting `status:'success'` — the same signature-verification discipline every real driver must follow, exercised end-to-end even though there's no real gateway on the other end. The signing secret reuses `env.APP_ENCRYPTION_KEY` (already a required, always-present 32-byte hex secret) rather than adding a new dedicated `MOCK_GATEWAY_SECRET` env var, specifically because the `mock` driver's whole purpose is "zero credentials needed" — adding a var that still defaults to something insecure-but-present would have been pure ceremony. `signMockToken`/`verifyMockToken` are exported (mirroring `bunny.js`'s exported `buildBunnyToken`) so `server/tests/adapters/payments/mock.test.js` can unit-test the builder/verifier directly against a self-computed deterministic vector, plus forged-token/cross-order-replay/missing-field rejection cases.

## 2026-08-05 — Phase 9.3 (integrations-dev): JazzCash `PaymentGateway` driver — real hosted-checkout hash algorithm, sourced live

**Context:** `docs/07_EXECUTION_PLAN.md` 9.3 — the first REAL (non-mock, non-placeholder) `PaymentGateway` driver, plugging into the factory + shared success path built in the 2026-08-01 entry above. Per the task brief's own explicit warning, training-data memory was NOT trusted for JazzCash's secure-hash algorithm; it was pulled live from JazzCash's own official sandbox docs site and cross-checked against a real, running community reference implementation before writing a single line of the driver. Full source list + exact quoted sections live in `server/src/adapters/payments/jazzcash.js`'s own header comment (kept there rather than only here, since that's where a future maintainer will actually look when the algorithm needs re-verifying against a doc revision).

1. **Which JazzCash product/flow this targets: the "Payment Portal" hosted-checkout HTML-form-POST flow, `pp_TxnType=MWALLET`** — matches `docs/02_ARCHITECTURE.md` §7's explicit "hosted-checkout pattern" (customer enters wallet/mobile-account credentials on JazzCash's OWN page, never ours). Sourced from the official PDF "Payment Gateway – Payment Portal Integration Guide for Merchants v4.2" (09 May 2019), fetched live from `https://sandbox.jazzcash.com.pk/SandboxDocumentation/Content/documentation/Payment%20Gateway%20Integration%20Guide%20for%20Merchants-v4.2.pdf` (converted to text via `pdftotext -layout`, since `WebFetch` alone couldn't extract readable text from this particular PDF's structure) — §6.1 "Payment Portal – Input Parameters" gives the exact field set for this form (`pp_Version, pp_TxnType, pp_Language, pp_MerchantID, pp_SubMerchantID, pp_Password, pp_BankID, pp_ProductID, pp_TxnRefNo, pp_Amount, pp_TxnCurrency, pp_TxnDateTime, pp_BillReference, pp_Description, pp_TxnExpiryDateTime, pp_ReturnURL, pp_SecureHash, ppmpf_1..5`), confirms `pp_Amount` is the smallest-currency-unit integer with no decimal point ("100.00 will be passed as 10000" — confirms `toCents()` reuse is correct), and gives the `pp_TxnDateTime`/`pp_TxnExpiryDateTime` format as `yyyyMMddHHmmss` (14 digits, sample `20110909203547`).

2. **The exact secure-hash algorithm (§14.1/§14.2 of the same PDF, cross-checked against `https://github.com/rafayhingoro/jazzcash/blob/master/jazzcash.php`'s real, running `secureHash()`/`genString()` code):** collect every `pp_`-prefixed field with a non-empty value (the community implementation's `!empty() && !is_null()` filter is the one detail the PDF's prose doesn't spell out explicitly, even though its own worked examples happen to have no empty fields to begin with); sort the field NAMES ascending by ASCII value (doc's own example: "Card should come before CardNum" — a plain string comparison naturally satisfies this, verified by a dedicated test); concatenate the VALUES ONLY (never the field names) in that sorted order, joined by `&`; prepend the Integrity Salt followed by `&`; compute `HMAC-SHA256(message, key=IntegritySalt)`; hex-encode (uppercase, matching every sample hash shown in the official PDF — `verifySecureHash` still compares case-insensitively on the RECEIVED side, since that casing convention isn't contractually documented anywhere). The PDF's own §14.2 worked example gives the exact intermediate MESSAGE string for a 3-field case (`0F5DD14AE2&2995&MER123&A48cvE28`) but never prints the final HMAC digest number for it — same situation `server/src/adapters/video/bunny.js`'s doc-gap note already established a precedent for (2026-07-31 entry, above) — so `jazzcash.test.js` uses the documented MESSAGE as a literal assertion, then self-computes the final digest via Node's own `crypto.createHmac` for the "does this equal what my implementation produces" half, rather than trusting an unpublished number.

3. **`createCheckout()` returns `{ actionUrl, method:'POST', formFields }`, not `{ redirectUrl }`.** JazzCash's Payment Portal is a form-POST target requiring a 64-char `pp_SecureHash` (and a dozen other fields) that cannot be encoded into a bare querystring redirect the way `mock.js` does — `docs/02_ARCHITECTURE.md` §7's own driver-return-shape note already anticipates `formFields` as a valid shape for exactly this reason. Documented in the driver's own doc comment for whoever wires the frontend in `docs/07_EXECUTION_PLAN.md` 9.7: render a hidden-input form, `method="POST"`, `action={actionUrl}`, auto-submit. Sandbox/production action URLs (`https://sandbox.jazzcash.com.pk/CustomerPortal/transactionmanagement/merchantform/` / `https://payments.jazzcash.com.pk/CustomerPortal/transactionmanagement/merchantform/`) are a judgment call in the sense that the PDF itself only references a server-side config placeholder for this URL, not a literal string — sourced instead from this exact endpoint appearing identically across multiple independent public JazzCash integration write-ups (WebSearch cross-check, 2026-08-05), which is as close to "vendor-confirmed" as this specific detail gets without a live merchant sandbox account.

4. **`pp_TxnRefNo` format `T{orderId}.{unixSeconds}` is an original judgment call**, not something JazzCash's docs mandate. JazzCash requires a fresh, unique `pp_TxnRefNo` per checkout attempt (retries need a new one) but ALSO echoes it back verbatim in every response (§6.1 response table: "As provided in the request"), so embedding our own order id in a parseable prefix is how `handleCallback()` recovers `orderRef` without needing any extra non-`pp_` merchant field (deliberately avoided using `ppmpf_1..5` for this — whether JazzCash's "all fields beginning with PP" hash rule in §14.2 also means to include `ppmpf_` fields, which begin with the same two letters but a different literal prefix, is itself a genuine ambiguity the docs don't resolve; sidestepping it entirely by not using those fields was simpler and strictly safer than guessing). `.` is used as the delimiter specifically because §6.1 names it as one of only two extra characters (`/` and `.`) the field allows beyond alphanumeric.

5. **`pp_TxnDateTime`/`pp_TxnExpiryDateTime` are rendered in Pakistan Standard Time (fixed UTC+5, no DST), not UTC** — a judgment call, since neither §6.1 nor §14 states a timezone for these fields, but a Pakistani payment processor's own transaction-datetime field is far more likely to expect Pakistan local time than UTC (and every sample value tested against real merchant integrations elsewhere used the same fixed-offset assumption). Computed via a plain millisecond-offset shift on `Date`, no new timezone-database dependency added (CLAUDE.md §4: keep dependencies minimal) — safe specifically because Asia/Karachi has had no DST changes since 2009.

## 2026-08-05 — Phase 9.4 (integrations-dev): EasyPaisa `PaymentGateway` driver — sparse-docs gateway, cross-checked against 3 real reference implementations

**Context:** `docs/07_EXECUTION_PLAN.md` 9.4, mirroring the JazzCash driver's rigor exactly per the task brief. EasyPaisa's public documentation turned out to be materially sparser than JazzCash's, exactly as the task brief anticipated: no equivalent of JazzCash's single authoritative sandbox-hosted PDF (`Payment Gateway Integration Guide for Merchants v4.2`) could be reached in a form `WebFetch` could extract full readable text from — the closest analog, "Easypaisa Merchant Integration Guide v4.1.2", is only mirrored on scribd/pdfcoffee behind preview walls that yielded metadata/summaries, never the actual parameter tables. Per the brief's own documented fallback for this situation, the algorithm was cross-checked for CONVERGENT agreement across three independent, real, running community reference implementations (fetched via raw GitHub content, not just search-engine summaries) before writing any driver code. Full source list + exact quoted/paraphrased evidence lives in `server/src/adapters/payments/easypaisa.js`'s own header comment.

1. **Which EasyPaisa product/flow this targets: the "Post Method" hosted-checkout HTML-form-POST to `Index.jsf`, `paymentMethod=MA_PAYMENT_METHOD`** — NOT EasyPaisa's separate, newer REST "Open API" (`/easypay-service/rest/v4/initiate-ma-transaction` etc., confirmed via `github.com/moeen-basra/omnipay-easypaisa`'s real Omnipay driver source), which authenticates via HTTP Basic `username:password` credentials rather than a Store ID + Hash Key pair. This codebase's reserved env vars (`EASYPAISA_STORE_ID`, `EASYPAISA_HASH_KEY` — already zod-validated in `server/src/config/env.js` from the 2026-08-01 foundation work, no schema change needed) only support the Hash-Key-based flow, which independently confirms this was the intended target before any driver code was written. `MA_PAYMENT_METHOD` (Mobile Account) was picked, over the also-real `CC_PAYMENT_METHOD`/`OTC_PAYMENT_METHOD` constants, as the closest EasyPaisa analog to JazzCash's `pp_TxnType=MWALLET` choice — a documented judgment call, since this codebase exposes exactly one `easypaisa` gateway code and EasyPaisa's own hosted page supports multiple channels.

2. **The hash algorithm — HIGH confidence, 3-way corroborated:** build `key=value&key=value&...` (raw concatenation, not URL-encoded, no trailing `&`) from a fixed field set in ascending alphabetical key order (`amount, autoRedirect, expiryDate, orderRefNum, paymentMethod, postBackURL, storeId`); encrypt with **AES in ECB mode, PKCS7-padded**, keyed by the raw UTF-8 bytes of the Hash Key (never hex-decoded); base64-encode the ciphertext; field name **`merchantHashedReq`**. Sourced from `github.com/FahadYousafMahar/Easypay-WHMCS-Gateway` (a real WHMCS-Marketplace-listed gateway module — `getHashedRequest()`), `github.com/maan56/EasyPaisa-Integration-PHP-Laravel` (`DepositController.php`'s `sorted_string`/`openssl_encrypt('aes-128-ecb', ...)`), and `github.com/zfhassaan/easypaisa` (a maintained Packagist Laravel package). This codebase's Node implementation dynamically picks `aes-128/192/256-ecb` by Hash Key byte length (16/24/32), matching the WHMCS module's own explicit `strlen($hashKey)==16||24||32` validation — `mcrypt`'s legacy `RIJNDAEL_128` (128-bit BLOCK, not fixed key size) auto-selected the AES variant by key length, which Node's `crypto` requires spelling out explicitly. Verified in this environment: encrypt-then-decrypt round-trips back to the original plaintext for all three key lengths (`server/tests/adapters/payments/easypaisa.test.js`). **Not** cross-checked byte-for-byte against a real PHP `openssl_encrypt()` output — no PHP runtime was available in this environment — but PKCS7-padded AES-ECB via OpenSSL is extremely standard, well-documented behavior, not itself an ambiguous claim; the genuine uncertainty here was the FIELD SET and field NAME, both independently triangulated across the 3 sources above.

3. **`amount` format: one fractional digit, decimal-point PKR string (e.g. `"15000.0"`), NOT a smallest-unit integer like JazzCash's `pp_Amount`.** 2-of-3 sources (`number_format($amount,1,'.','')` in the WHMCS module; `$request->amount.'.0'` in maan56's controller) agree exactly, corroborated further by a WebSearch-indexed excerpt of the (unreachable-in-full) official guide's own text describing "Post Method Integration ... one decimal point (e.g., 10.0)" for this same flow. A separate, unrelated Mastercard/MPGS "Hosted Checkout" product page's "last two digits are decimal" phrasing surfaced in the same searches and was discarded as noise (different vendor, different product). `formatEasypaisaAmount()` derives this from `toCents()`'s exact-integer-cents value (never a float multiply, per `server/src/utils/money.js`'s house rule), rounding the DECIMAL(10,2) column's 2nd fractional digit to the nearest 0.1 half-up — a minor judgment call, since none of the 3 sources' own demo amounts ever needed to round a genuine non-zero 2nd decimal digit.

4. **CONFIRMED, GENUINE DOC GAP — inbound callback has no documented cryptographic signature (LOW confidence, most consequential judgment call in this task).** EasyPaisa's own documented postback fields (`status` ∈ {"Success","Failure"}, `desc` ∈ {"0000","0001"}, `orderRefNumber`) — corroborated by maan56's real, running `checkoutSuccess()` (`$request->desc == "0000"`) and a WebSearch-indexed excerpt describing the same three field names from the merchant-portal docs — carry **no signature field in any of the 3 independent implementations inspected**, a stark contrast with JazzCash's `pp_SecureHash`. The one source with genuine anti-spoofing logic (the WHMCS module's `callback/EasyPay.php`) instead validates that a provided `url` param is hosted on `*.easypaisa.com.pk` via regex, then performs a server-to-server `cURL` GET to that URL to fetch the AUTHORITATIVE transaction JSON — a fundamentally different "fetch from source of truth" verification model, not a per-callback signature, and one this driver's synchronous, credential-light contract can't safely replicate (no username/password reserved anywhere for the REST "Inquire Transaction Status" API either, and replicating it would need a live sandbox account to validate against, which isn't available). One WebSearch result surfaced text resembling an imperative instruction to "verify merchantHashedResp on every callback... a response code of 0000 alone is trivially spoofable from curl" — its phrasing read as out-of-register for genuine vendor documentation (more like injected/manipulative content than doc prose per the tool's own untrusted-content guidance), so it was explicitly NOT used as a source for a field name or design decision; noted here only as a provenance flag, not acted on.
   Given CLAUDE.md's hard "verify signatures on EVERY callback" requirement and this driver's own contract ("NEVER assume `signatureValid` true"), the decision made: **this driver imposes its OWN defensive requirement, not specified by EasyPaisa itself** — the caller must supply a `merchantHashedReq` field on the callback, computed with the identical AES-ECB(HashKey) primitive as the outbound request, but over the callback's own terminal fields (`desc, orderRefNumber, status, transactionId`, non-empty only). This gives genuine protection against anyone without the shared Hash Key forging a fake "paid" callback against THIS codebase's `/webhooks/payments/easypaisa` route (proven by `easypaisaFlow.e2e.test.js`'s forged-hash test: order stays `pending`, event logged with `signatureValid:false`), but it is **not confirmed to be what a real EasyPaisa server actually sends** — flagged prominently in the driver's own file header (source note 4) so a future maintainer with real sandbox/merchant-portal access can verify or replace this the moment credentials exist. This is the single biggest confidence gap in this task, by design kept safe-by-default (an unverifiable callback simply never pays the order) rather than either fabricating false certainty or skipping verification altogether.

5. **`orderRefNum` format `E{orderId}T{unixSeconds}` is an original judgment call**, alphanumeric-only (no `.`/`/`, unlike JazzCash's `pp_TxnRefNo`) to match the WHMCS module's documented "Max 20 Alpha-Numeric characters" constraint — the letter `T` is used as an alphanumeric-safe delimiter instead of JazzCash's `.`. The response-side field name is `orderRefNumber` (note the trailing `s`/different word from the request's `orderRefNum`) — a genuine, corroborated asymmetry (WHMCS callback.php reads `$_REQUEST['orderRefNumber']`; the WebSearch-indexed doc excerpt for postback fields also says `orderRefNumber`), deliberately preserved rather than "fixed" to a single consistent name, since using the wrong one would make this driver silently fail to parse a real gateway's callback.

6. **`createCheckout()` returns `{ actionUrl, method:'POST', formFields }`, not `{ redirectUrl }`** — same reasoning and shape as `jazzcash.js` (a 64+-char `merchantHashedReq` plus half a dozen other fields cannot be safely encoded into a bare querystring redirect). Sandbox/production action URLs (`https://easypaystg.easypaisa.com.pk/easypay/Index.jsf` / `https://easypay.easypaisa.com.pk/easypay/Index.jsf`) are HIGH confidence — identical literal strings appear in all 3 independent reference sources.

## 2026-08-05 — Phase 9.5 (Raast) + 9.5b (PayFast/Safepay placeholders) + 9.6 (bank transfer + shared admin approval queue)

**Context:** `docs/07_EXECUTION_PLAN.md` 9.5/9.5b/9.6, dispatched together as one tightly-coupled manual-payment lifecycle. Unlike JazzCash/EasyPaisa (2026-08-05 entries above), Raast and bank transfer are NOT real API integrations — both are manual pseudo-gateways sourced entirely from this app's OWN admin-editable `settings['payments']` row, with a human admin approval step standing in for a gateway's own signature-verified callback. 1. **The proof-image storage/serving design — the trickiest part of this task.** Full writeup also lives in `server/src/services/manualPaymentService.js`'s own file header (the canonical copy a future maintainer will actually read).
   - **Physical file:** `storage/proofs/order-{orderId}.bin` — a DETERMINISTIC filename keyed purely by the order's own id, deliberately mirroring `services/invoiceService.js`'s own precedent (`{invoiceNo}.pdf`, never a generated token) rather than `adminUploadService.js`'s random-token pattern. `bank_transfer_proofs.order_id` is already `UNIQUE` in the schema, so "one proof image per order" is already the correct invariant everywhere else this table is touched — a re-upload for the same order simply `fs.writeFile`-overwrites the previous file (default `'w'` flag truncates), so there is never an orphaned old file needing separate cleanup, and no extra DB column is needed to track a generated filename/token at all.
   - **Content-Type is sniffed at SERVE time**, not stored: `GET /orders/:id/proof-image` reads the file and calls the SAME `sniffImageType()` the upload step already used to validate it, rather than persisting/trusting an extension or client-declared mimetype anywhere. This sidesteps needing an extra DB column or a filename-encodes-the-extension scheme entirely.
   - **`storage/proofs/` is NOT statically served** — sibling to `storage/uploads/` but with no `express.static` mount in `server/src/app.js` (added the mirror-image `.gitignore` entries: `storage/proofs/*` + `!storage/proofs/.gitkeep`), for the exact reason `services/invoiceService.js`'s own header already documents for invoice PDFs: a payment-proof image may contain a real bank receipt with financial details, so access control has to happen in an authenticated route, never via an unguessable filename alone.
   - **`bank_transfer_proofs.file_path` (pre-existing schema column) stores the RAW on-disk relative path** (`proofs/order-{id}.bin`) — an internal implementation detail. `orderService.js#serializeProof` was extended to NEVER echo this raw value back to any API response; it computes `buildProofImageUrl(orderId)` (a new exported `orderService.js` function, `/api/v1/orders/{orderId}/proof-image`) instead, exactly once, in exactly one place. This is the exact same "raw disk location is internal, never exposed raw" discipline `invoiceService.js` already established, just applied one level differently (a computed URL string instead of a computed disk path) since `bank_transfer_proofs.file_path` — unlike invoice PDFs — is a real, pre-existing DB column the frontend's `Order.proof.filePath` type already expects to read something browser-consumable out of (confirmed directly: `client/src/pages/admin/ManualPaymentsPage.tsx` renders `<img src={row.proof.filePath}>`).
   - **Upload -> order linkage happens IMMEDIATELY at upload time, not later**, resolving the task brief's own open design question. `POST /checkout/uploads/proof-image` requires an `orderId` multipart field alongside `file` — the frontend already has the order id at this exact point in the real UX (the order was just created moments earlier by `POST /checkout/orders`, which is what surfaced the `manualDetails`/payment instructions the student is now acting on), so there is no genuine "unlinked upload" period needing its own tracking table. `uploadProofImage()` upserts the SAME `bank_transfer_proofs` row `submitBankProof()` later updates, keyed by `orderId` (`findOrCreate`, never a blind `create()` that would throw on a second upload attempt for the same order — re-uploading a replacement image alone does NOT reset an already-reviewed proof's status/reference/note; only a genuine `bank-proof` (re)submission does that).
   - **`fileUrl` on `POST /checkout/orders/:id/bank-proof` is never blindly trusted**, per the task brief's explicit instruction: `submitBankProof()` re-derives the EXPECTED url via the exact same `buildProofImageUrl(orderId)` function the upload step used, and requires (a) the client-submitted `fileUrl` to match it EXACTLY and (b) a `bank_transfer_proofs` row with a non-null `filePath` to already exist for this order — i.e. the upload step must have genuinely run first, for THIS SAME order/user, before bank-proof can be submitted (`422 PROOF_IMAGE_REQUIRED` / `422 VALIDATION_ERROR` otherwise). A student can never submit an arbitrary/guessed/someone-else's URL string as if it were their own uploaded proof — proven by `tests/checkout/bankTransferFlow.e2e.test.js`'s dedicated mismatched-fileUrl test.
   - **`GET /orders/:id/proof-image`** (added to the existing `server/src/routes/v1/orders.js`/`ordersController.js`, mirroring `downloadInvoice()`'s exact pattern rather than inventing a new route family) is owner-or-admin only via `orderService.js#assertViewerCanAccessOrder` (exported, reused — the SAME IDOR rule `GET /orders/:id/invoice.pdf` already enforces), keyed off the ORDER id in the URL, never off the file's own name. Served as a plain `res.send(buffer)` (not `res.sendFile`, since the buffer was already read into memory to sniff its Content-Type) — works correctly as a plain `<img src>` browser request since same-origin `httpOnly` auth cookies are sent automatically, no `Authorization` header needed, confirmed by `ManualPaymentsPage.tsx`'s own direct `<img src={row.proof.filePath}>` usage.

2. **`isConfigured()` for `raast`/`bank_transfer` is `true`, ALWAYS, synchronously, with zero I/O — a deliberate, documented deviation from a literal reading of this task's own brief** ("isConfigured() — true iff the relevant Settings fields are non-empty... read from `Setting.findByPk('payments')`"). That literal instruction would require `isConfigured()` to do real DB I/O and therefore be `async` — but `server/src/adapters/payments/index.js#isGatewayAvailable`/`#getPaymentGateway` are SYNCHRONOUS and are asserted on synchronously, WITHOUT `await`, by `tests/adapters/payments/{index,jazzcash,easypaisa}.test.js` — two of which (`jazzcash.test.js`, `easypaisa.test.js`) are explicitly protected/off-limits-to-modify files for this task. Making `isConfigured()` async here would make `!driver.isConfigured()` (in `index.js`'s existing, unmodified gate logic) evaluate the truthiness of a `Promise` object — always truthy — silently breaking that gate for EVERY driver, not just this one, the moment `raast`/`bank_transfer` were registered. Resolution: the REAL "are Settings actually filled in yet" check — the one the task brief actually cares about — was moved into `createCheckout()` instead, which is already `async`, already does real I/O, and is already the natural place every OTHER reason a checkout can't proceed gets surfaced. It throws the SAME `422 GATEWAY_NOT_CONFIGURED` code a synchronous factory-level rejection would have produced, so the CLIENT-OBSERVABLE behavior (a 422 with that exact code when Settings aren't filled in) is unchanged from the brief's intent — only WHICH layer performs the check moved. Verified by `raast.test.js`/`bankTransfer.test.js`'s own "fresh/unconfigured DB" and "incomplete Settings" test cases.

3. **Two separate driver files (`raast.js`, `bank_transfer.js`), not one shared module** — each needs its own `code` and its own, genuinely different minimum-required Settings field set (`raast`: `raastId`+`raastIban`; `bank_transfer`: `bankName`+`accountTitle`+`iban`), even though `createCheckout()`'s `manualDetails` SHAPE and `handleCallback()`'s always-failing-no-op body are byte-for-byte identical between the two. The genuinely-shared piece (reading+defaulting the `settings['payments']` row) was factored into `server/src/adapters/payments/manualGatewayShared.js`'s `readPaymentsSettings()` so it's never duplicated/drifted between the two driver files — matching this codebase's existing "small shared helper, not a shared driver object" convention.

4. **`manualDetails` field-reuse-for-both-gateways**, matching `client/src/api/endpoints/checkout.ts`'s `CreateOrderResponse.manualDetails` type EXACTLY (one shared interface, confirmed by reading that file directly, not guessed): `{raastId, iban, accountTitle, bankName, qrImageUrl}`. For `bank_transfer` orders, `raastId`/`qrImageUrl` are returned as empty strings (not omitted/undefined) since they're not applicable to a plain bank transfer — `accountTitle`/`bankName` are shared between the two gateways since both ultimately settle into the SAME underlying bank account Settings > Payments describes. 5. **`handleCallback()` on both manual drivers is a safe, ALWAYS-FAILING no-op** (`status:'failed'`, `signatureValid:false`, `eventType:'payment.callback.unsupported_manual_gateway'`) rather than omitted entirely, per the task brief's own instruction — these two gateways are never actually reached via `GET /checkout/return/:gateway` or `POST /webhooks/payments/:gateway` in real operation (the admin approval queue, `manualPaymentService.js`, is the ONLY path that ever completes a `raast`/`bank_transfer` order), but a driver must stay interface-conformant with the contract every driver satisfies, and a forged/stray request against either generic route with `gateway=raast`/`bank_transfer` must never be able to fake a successful payment. A short commented-out slot for a FUTURE direct Raast API driver (a different gateway code, e.g. `raast_api`) was left at the bottom of `raast.js`, per `docs/02_ARCHITECTURE.md` §7's own note — Raast itself (the State Bank of Pakistan's instant-payment settlement rail) exposes its real APIs to licensed financial institutions, not individual merchants, so no external doc research was attempted or needed for this driver, unlike JazzCash/EasyPaisa.

6. **Admin approve — order of operations chosen specifically to avoid a stuck "approved but not actually paid" inconsistency.** `approveBankTransfer()` calls `orderService.js#completeOrderPayment()` (THE shared success path, unmodified, reused exactly as every other gateway uses it) FIRST, and only marks `bank_transfer_proofs.status='approved'` + reviewer fields AFTER it genuinely succeeds — not before. If `completeOrderPayment()` throws (e.g. a concurrent order exhausts a shared coupon — the same real race `docs/07_EXECUTION_PLAN.md` 9.2's own coupon-abuse AC already covers for every other gateway), the proof is deliberately left `pending` rather than risking a stuck "approved" proof on an unpaid order; the admin can simply retry. If `completeOrderPayment()` reports `alreadyProcessed:true` (a concurrent SECOND admin-approve click raced this one and the order's own row lock resolved it first), this throws the SAME `409 ALREADY_RESOLVED` the losing racer should see — the proof is never double-written, since only the WINNER of `completeOrderPayment()`'s own atomic order-row lock ever reaches the `proof.save()` line. This achieves correct at-most-once approval semantics without needing a SEPARATE row lock on the proof itself (simplicity first) — verified by the e2e test's own "re-approving an already-paid order -> 409, not double-processed" case.

7. **Admin reject -> `orders.status='failed'` is a confirmed judgment call, sourced directly from the already-built frontend's own copy text**, per the task brief: `client/src/pages/admin/ManualPaymentsPage.tsx`'s reject-confirmation modal literally reads "Rejecting this payment request will mark the order as failed" — there is no separate `'rejected'` value in `docs/03_DATABASE_SCHEMA.md`'s `orders.status` ENUM, and `'failed'` is a legitimate, already-existing terminal status. `rejectBankTransfer()` runs as its own short row-locked transaction (this service fully controls the mutation end-to-end, unlike approve which delegates to `completeOrderPayment()`'s own transaction) setting `orders.status='failed'` + `bank_transfer_proofs.status='rejected'`/`reject_reason`/reviewer fields atomically, then best-effort notifies the student (`Notification.create` + optional email, mirroring `orderService.js#sendPurchaseConfirmation`'s own non-blocking style exactly, new `type:'purchase_rejected'`). A rejected order has no in-place retry — the student must place a fresh order — consistent with how a declined JazzCash/EasyPaisa payment already works everywhere else in this codebase (no in-place retry-same-order flow exists anywhere yet, for any gateway).

8. **`GET /admin/bank-transfers?status=pending` query implementation simplified from a literal `orders.status OR proof.status` join to a single `orders.status` filter** — a deliberate, documented simplification, not an oversight. `docs/04_API_SPEC.md` §7 describes the queue as "orders with `status='awaiting_verification'` OR an associated proof with `status='pending'`", which would naturally suggest a `$bankTransferProof.status$`-keyed `Op.or` association-where query. But `submitBankProof()`/`approveBankTransfer()`/`rejectBankTransfer()` in THIS implementation always transition `orders.status` and `bank_transfer_proofs.status` TOGETHER, atomically, in every single code path that touches either — meaning "has an associated proof with `status='pending'`" is PROVABLY equivalent to "`orders.status='awaiting_verification'`" in this codebase, always.
