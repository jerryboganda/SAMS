### Index added

**`idx_taq_q_answered_correct` on `test_attempt_questions(question_id, answered_at, is_correct)`** — migration `server/src/db/migrations/20260101000036-add-perf-indexes.cjs`.

**Justification (EXPLAIN, baseline run):** `buildTopSubjectsAttempted`'s join drove from `questions` (already efficient — an index-only scan via `fk_q_subject`, 9,769 rows) and then, for **every one of those ~9,769 matched question rows**, did a `ref` lookup into `test_attempt_questions` via the existing `idx_taq_q` index (`question_id` only) with **`Extra: Using where`** (not `Using index`) — meaning every matched row (roughly 80,000 total, `rows: 8` x 9,769 probes) required an extra random-IO fetch of the full base row just to read `answered_at` (the WHERE filter) and `is_correct` (the GROUP BY/SELECT column), neither of which the old index covered.

The new index extends that access path into a genuinely **covering** index: MySQL can now satisfy the `answered_at IS NOT NULL` filter and read `is_correct` directly from the index leaf, with **zero base-row lookups** (`COUNT(TestAttemptQuestion.id)` remains satisfiable too, since InnoDB secondary indexes implicitly carry the clustering primary key). Confirmed directly in the "after" EXPLAIN output above (statement 6): `key: idx_taq_q_answered_correct`, **`Extra: Using where; Using index`**.

The existing `idx_taq_q` (`question_id` only) was deliberately **left in place**, not dropped — `qbankService.js#assertQuestionSeenByUser` and other simple `question_id`-only lookups still benefit from the narrower, cheaper single-column index, and this migration's brief is additive ("add missing indexes"), not a general index audit.

### Judgment calls

- **Idempotency (`seedSyntheticLoad.js`):** full schema reset (`db:migrate:undo:all` + `db:migrate`, both `--env perf`) on every run, rather than a `--force` flag or per-table `TRUNCATE`. This reuses the exact mechanism `server/tests/globalSetup.cjs` already established for the jest test DB, guarantees the perf DB is always on the current migration set (including this task's own new index migration), and avoids hand-maintaining FK-aware `TRUNCATE` ordering across ~35 tables. The whole reset+reseed cycle takes ~20s — a non-issue for a script that is only ever run by hand, opt-in, for a perf investigation.

- **Perf-DB isolation in this specific sandbox:** the configured `DB_USER` (`sams_app`) has `ALL PRIVILEGES` pre-granted only on 4 specific, already-named databases (`sams_academy`, `sams_academy_test`, `sams_dev`, `sams_test`) — not a global `CREATE DATABASE` privilege, and not a grant on the literal name `sams_academy_perf`. `CREATE DATABASE IF NOT EXISTS sams_academy_perf` genuinely fails as this user (`Access denied ... to database 'sams_academy_perf'`), confirmed empirically while building this suite. For this sandbox, `server/.env`'s local (gitignored) `DB_NAME_PERF` was set to `sams_test` — one of the two pre-granted-but-previously-empty schema slots — so the perf DB used in this run is physically named `sams_test`, **never `sams_academy` or `sams_academy_test`**. The code-level default (`server/src/config/env.js`, `.env.example`) stays `sams_academy_perf`, matching `DB_NAME_test`'s naming convention, for a properly-provisioned environment; `lib/perfDb.js#ensureDatabaseExists()` surfaces a clear, actionable error (with the one-time bootstrap `GRANT` statement) if the configured user lacks the necessary privilege for whatever name is configured, rather than failing with a bare MySQL error.

- **Shared-test-DB contention while verifying Part C (see `HANDOFF.md`'s own documented lesson):** the first full `npm run test` run after adding the migration failed broadly (116/874 tests, 36/93 suites) with widespread, unrelated-looking 500 errors. Root-caused (not a regression from this task's own migration): another concurrent phase's agent process was also running `db:migrate:undo:all`/`db:migrate` against the same shared `sams_academy_test` database at the same time, and the two runs' migration-history bookkeeping desynced from the physical schema — `SequelizeMeta` reported `20260101000035-fix-enrollment-active-unique-and-reminder-column.cjs` as applied while its actual columns (`expiry_reminder_sent_at`, `active_slot`) were physically absent from the table, causing `Unknown column` errors on essentially any query touching `enrollments` (which is most of the app). This was reconciled by removing the stale `SequelizeMeta` bookkeeping row for that one migration and letting `db:migrate` re-apply it cleanly (a live-data repair, not a code change — that migration file itself was not modified). After that reconciliation, a solo, uncontended `npm run test` run passed **93/93 suites, 874/874 tests, 100% green**, confirming the new index migration introduces no regressions.
